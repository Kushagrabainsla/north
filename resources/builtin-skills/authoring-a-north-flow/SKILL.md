# Authoring a North flow

> A flow is an executable, ordered process. The user's outcome is the goal; creating YAML is only one setup step.

## Procedure
1. Restate the requested outcome and completion evidence. Separate the trigger, ordered work, user-review boundary, and any prohibited final action.
2. Search existing flows, skills, tools, agents, and schedules. Reuse or compose them before creating another entity. Flows invoke skills; skills may call several atomic tools. If a procedure is missing, create or improve the skill. If an atomic capability is missing, identify that tool gap first.
3. Complete the setup checklist below before calling `create_flow:create`. Ask for every unresolved user choice with `ask_user`, one concise question at a time; retain earlier answers and do not ask again for details already supplied. Discover technical facts instead of making the user research them. For browser work, discover saved profiles and select an enabled `profile_id` per browser tool call using task context and configured purposes. If missing or ambiguous, ask which browser profile to use through the same central mode policy. Explain access to sessions/cookies/tabs/extensions and run a login and dependency preflight. Profiles belong to tool calls, never flow definitions or flow inputs. A profile name alone is not proof of attachment. Never silently switch profiles or copy cookies as a fallback. If already signed in to the expected account, reuse the session without requesting another login. Saved passwords alone do not prove an active login. Ask for sign-in help only if the site requires it (expired session, MFA, or password-manager unlock); do not read or export passwords or ask for them in chat. A connection failure is a setup blocker, not a login problem.
   - If the user replies with a question instead of resolving the choice, answer it and ask the unresolved choice again in the same run. A clarification is not completion.
   - If the person must sign in, complete MFA, unlock, or take over the browser, call `ask_user` with `requires_user_action=true` as its own tool call. Explain the needed action and offer "Done". This follows the same central mode policy as every other question. A pending request pauses the original task; after any answer, inspect and assert the expected account or state before continuing in the same profile. An automatic answer is not proof of login. Waiting is not failure or completion. Do not repeat completed external actions or loop on automatic answers; stop if the person cancels or declines.
4. Check feasibility against the live capability catalog. Every executable step must select a skill with an execution contract, give concrete instructions, and bind its inputs. A skill is live once it passes its own tests; a draft skill can still be used in a flow's test run. Normal runs require live skills. The skill contract owns the executor and exact tool allowlist. Never put an agent or tool directly in a flow step.
5. Define bounded behavior in each skill contract: inputs, outputs, allowed tools, limits, timeouts, retries, persistent deduplication, minimum approval, and clear success criteria. Never use "all" without a safe maximum.
6. Encode safety as executable policy. `never` blocks mutating tool calls, `on_mutation` asks immediately before each mutating tool call, and `before_step` asks once before the skill step begins, then lets it run (`always` still loads as an old name for it). "Do not submit" in prose is insufficient.
7. Call `create_flow` to create the flow, or update the existing flow when it already owns the process, with `test_inputs` for the smallest safe case. The user is asked once; the flow is then checked, run once as a test, and is live if the test completes. The test executes real tools and is not a dry run: each step still asks as its approval says. If the test fails, a new flow stays a draft and an edit goes back to the version that was live; read the error, fix it, and call again. A draft that already exists goes live with `action=activate`. Do not install a schedule before the flow is live.
8. Verify the test's expected output, prohibited actions, state persistence, and failure behavior from its run record, not from the call returning.
9. If one-time or recurring timing was chosen and installation is confirmed, use the existing `schedule_task` tool, read the schedule back, and verify its next firing. Manual-only flows need no schedule. If the user deferred testing or installation, keep the agreed timing in the setup summary and report the schedule as pending, not installed.
10. Report each state separately: created and live (or still a draft, with why), environment verified, schedule installed, and first successful run. Always report timing: manual only, requested timing pending installation, or verified installed timing and next firing. Green means the requested automation is operational, not that a file exists.
11. Treat tool actions as evidence, not tool names. `create_flow:list` or `create_flow:read` proves discovery only; a live flow requires a successful `create_flow:create`, `create_flow:update` or `create_flow:activate`.

## Setup checklist

- Outcome and evidence: what should each run achieve, and how will the user know it worked?
- Inputs and preferences: which sources, files, accounts, filters, and factual answers are needed? Which are saved choices and which will be supplied per run? Never invent personal facts; unresolved per-run values can remain declared required inputs if the user chose that design.
- Outputs and delivery: what artifacts or results, where they belong, and whether delivery is in chat, local files, or an explicitly permitted external destination.
- Scope and safety: workload limits, duplicate handling where relevant, review/approval boundaries, and actions that must never happen. Discover supported behavior; explain any capability gap before promising it.
- Timing is a required user choice, even if the prompt only says "create a flow". If timing was not explicitly supplied, call `ask_user`: "When should this flow run?" Offer "Manual only", "Once at a specific time", and "Recurring". Do not silently default to manual or assume that "automate" means daily. "Leave it a candidate", "do not activate yet", and "do not install a schedule yet" do not answer when the finished flow should run.
- Complete the chosen timing: for one-time work, the date and local time; for recurring work, either frequency/interval or days and local time. Always use the user's timezone configured in North settings, supplied in the trusted runtime context; timezone is not a flow input or question. Do not ask for timezone, declare a timezone input, or pass a per-schedule override. Name the settings timezone in the summary as read-only information. If settings cannot be read, report the configuration problem rather than guessing. "Recurring", "daily", or "in the morning" alone needs clarification. Do not invent 09:00 or weekdays. An explicitly requested interval needs no wall-clock time.
- Summarize the agreed outcome, inputs, outputs, limits, safety boundary, and timing before authoring. Missing choices mean setup is waiting for the user, not complete. Choosing timing is not approval to test, activate, or install it; use existing authoring and scheduling approval boundaries, not a second scheduler or a `schedule` field in `FLOW.yaml`.
- When updating a flow, read its definition and `list_schedules` first; preserve existing timing (cadence and local clock time) unless the user requests a change, and resolve timing if none was previously agreed. The timezone still comes only from North settings, not the flow.

## User-defined flows
- A user's custom workflow belongs in learned skills and flows created with `create_skill` and `create_flow`, not a new built-in or a repository edit. Read the existing definition before improving it; retain its name when it owns the process. Updating a user-authored definition requires a fresh approval and keeps a recoverable previous version.
- Translate the user's prompt into a narrow executable contract. If the requested result is local artifacts from saved inputs, allow only the file tools needed; do not reuse a broader browser, email, or submission procedure just because its topic matches. Prose prohibitions are not a tool boundary.
- Keep user-specific paths and preferences in flow inputs, bound with `${inputs.<name>}`. Ask for missing facts rather than inventing them. Check the resolved inputs before running.
- Test the smallest representative case, then a mismatch and an adversarial input where relevant. Inspect actual artifacts and tool evidence. Do not activate, schedule, or widen the scope merely to make a test possible.
- Authoring tools raise their own mutation approval cards. Do not add a duplicate `request_approval` for the same create/update; use `ask_user` only when a missing choice blocks the design.

## Done when
- Setup choices, including explicit timing, are resolved and summarized; supplied answers were not needlessly asked again.
- Existing capabilities were reused where possible, every referenced skill contract validates, the flow passed its test and is live, and any requested schedule exists.
- If North lacks a required runtime feature, stop at a draft and name the missing capability plainly.
